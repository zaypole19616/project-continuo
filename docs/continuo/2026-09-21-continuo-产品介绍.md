# Continuo 产品介绍

## 1. 对未来 Agent 产品交互、Harness 与模型发展趋势的判断

### 1.1 对产品交互的三个思考

我把人与 Agent 的协作体验分成两层。

一层是**显性交互**：是产品形态，是用户看到的界面，如以对话框为主的桌面端 Agent Codex、Manus，以 IM 交互为主的 grok bot 等等。移动互联网发展至今，不同的需求场景，早已有了最适配的产品交互形态。比如，用户在自己工作时，可以打开桌面端，在对话框里完成任务；和别人协作时，又可以回到 Slack 这样的协作软件里与 Agent 交互。这些形态可以互相配合，背后也可以由同一套 Agent Harness 支撑。我认为，产品形态应该去适配用户的需求场景。可能不存在唯一正确的交互，应该让 Agent 出现在用户最熟悉的产品形态下。

另一层是**隐性交互**：是 Agent 在执行与交付中让人感受到的做事方式，比如怎么了解资料、组织工作、保存成果。作为助理，我们会希望它把事情打理得井井有条。这有点像我们平时说的 P 人或 J 人，用户能感受到这个 Agent 是怎么做事的，也会因此对它形成不同的使用体验。

两层合在一起，才是完整的协作体验。围绕这两层，我有三个 bet。

### Orderliness · 有条理和章法

我希望 Agent 能把工作打理得有条理：资料、任务与成果各有归处，用户的做事方式及习惯能留下来，下次继续时不用从头交代。重点是选择性积累有效上下文：**留下有来源、有适用范围的客观信息。**

### Proactiveness · 主动但有分寸

主动型 Agent 最常见的失败，是把“让用户注意到我”当成目标：悬浮窗、鼠标旁的弹窗、不断的提醒。它本该减少负担，却在抢注意力。我认为好的主动是润物细无声的：在已经明确委托的范围里把事情处理好，不需要人盯着；需要人作决定时，带着必要的信息来找我；我想查看进展、修改要求、接管或暂停，随时都能做到。

### Clarity · 坦诚与清晰

AI 发展迅速，新的概念或功能可能给用户带来较高的理解成本。以往的产品经验往往会让我们觉得，一款产品应该足够直观，没有任何教程或引导，凭直觉就能直接上手使用，但现在这样做反而可能提高用户的使用门槛。所以需要帮助用户理解什么对他们最相关，即便会增加理解成本或摩擦，也不要回避。

### 1.2 对 Harness 与模型发展趋势的判断

今天大家都在谈 Agent 的下一阶段能力：long horizon、递归自我改进。实际体验里，让模型做执行，完成某件事情的能力很强；但判断哪个方向更有价值、哪里值得继续投入，是它的弱项。模型在各类任务里常常分不清什么方向更有价值。我认为这是 long horizon、自我改进，乃至泛化到真实任务的共同卡点。

我认为这是当下比较难解决的问题，需要在模型、Harness，乃至产品交互这三个层面一起尝试解决，构建模型、Harness 与产品之间的反馈闭环。 

第一，**通过 Harness 提供有依据的不同路径，把方向交给人选择与判断，在各个决策的十字路口与人对齐。** 面对模糊任务，Harness 不要求模型一开始就选中“正确答案”，而是让 Agent 先提出几条有依据的可能路径，交给人带着自己的目标、偏好和约束来判断。选定方向后，Harness 让 Agent 沿这条路推进，再把实际结果带回下一轮判断。这样，模型负责探索和执行，人负责判断取舍，Harness 负责让每一轮选择影响下一轮工作；多个可能方向才会逐渐收敛为和人对齐的最佳路径。

第二，**让模型从带有人类判断与结果反馈的任务轨迹中学习，提高方向判断的能力。** 只看最终产物，模型学不到人为什么选这条路、后来又为什么放弃。把当时的条件、候选方向、人的选择与后续结果放在一起，才有可能比较哪些方向值得继续。尤其是改向和放弃的原因，能帮助理解为什么一条路不值得投入。这些轨迹可以作为后续评估和训练的材料，提升模型对方向的判断能力。

## 2. 产品功能

Continuo 是一个住在本地文件夹里的 Agent，基于 Kimi Code 实现。它把做过的事留在工作记录里，把值得继续的事交给用户处理，在方向不明时把选择交给人，并让每次选择都能沿着轨迹回看。

### 2.1 工作记录：把原始过程留在项目里

Continuo 会按日期、分类和事项，在项目的 `work-log/` 中自动生成工作日志：开始与结束时间、输入目录、实际读取的文件和输出文件，以及用户最初交代了什么、中途补充了什么、每轮怎样处理、还有哪些没完成。项目型任务的日志还包含 STAR，随执行与交付核验补全。用户在文件夹里就能找到日志和成果，下次也能从这里继续。

### 2.2 事项：把下一步变成用户可以处理的工作

了解项目或完成一件事后，Continuo 会根据实际资料提出下一步建议。建议是一种尚未开始的事项：用户可以立即执行、划掉，或留在待办里以后再做；自己添加的待办还可以设定时间。「事项」里能看到哪些工作正在进行、哪里等自己决定、哪些已经停下；用户随时可以暂停或继续，Agent 来问时可以回复、补充要求，权限设置决定 Agent 什么时候需要停下来确认。

事项也是可进一步体现主动性的地方：用户怎么处理待办，会教会 Agent 哪些事可以先接手、在权限内先做到需要人判断的地方再交回来。

### 2.3 决策：把方向交给人判断

当一件事有几条真正不同的做法时，Continuo 不替用户选，而是把候选方案及其依据、风险和适合的情况呈现出来，并说明选择取决于什么；只有材料足以支持时，才给出有理由的建议。用户可以选一条，也可以要求更多方向或提出自己的方向。选定后，Agent 沿这条路推进，再把实际结果带回下一轮判断。

### 2.4 轨迹：把方向选择和之后发生的事连起来

如果后来的结果改变了判断，用户可以回到当时的决策换一条路，或从已完成的某件事之后重新开始；原来的轨迹保留，新的工作从相应节点继续。另一条轨迹产出的文件不会被覆盖，Git 代码项目用独立 worktree 隔离改动。Agent 继续执行时只带当前路线的上下文，不会把另一条路后来的过程当成当前要求。

轨迹把任务条件、候选方案、人的选择、执行过程和后续结果连在一起，可以通过接口导出，供以后评估方向判断；当前原型尚未接入模型训练。

## 3. 如何体验

代码与运行说明在 [project-continuo](../../README.md)。需要 Node.js 24.15 及以上、pnpm 10.33 和可用的 Kimi Code 模型登录。在项目根目录运行：

```bash
pnpm install
pnpm run build:packages && pnpm -C apps/kimi-code run build
node apps/kimi-code/dist/main.mjs login
KIMI_CODE_EXPERIMENTAL_CONTINUO=1 node apps/kimi-code/dist/main.mjs web --no-open --port 58627
```

如果 `pnpm install` 因 Node 版本报 `ERR_PNPM_UNSUPPORTED_ENGINE`，改用 `pnpm install --config.engine-strict=false`。

另开一个终端运行 `KIMI_PORT=58627 pnpm dev:continuo`，然后打开 `http://127.0.0.1:5180/#token=<上一步服务启动时打印的 token>`。首次进入会看到功能介绍；没有登录模型时，打开项目后会提示先登录，登录后点「重新了解」即可。

仓库里的 [`examples/q4-plan`](../../examples/q4-plan) 是一份合成的第四季度线下活动策划资料：`AGENTS.md`、三个城市的简报和预算表。建议先把整个文件夹复制到仓库外，再用「打开已有项目」选择副本，避免试用时写出的日志和成果改动代码仓库。

可以沿这条路径试用：

1. 看 Continuo 如何了解文件夹，以及每条项目要点指向哪些资料；随后在文件区打开简报和预算。
2. 查看它提出的下一步事项（如果有），选择立即执行、划掉或加入待办；在右上角「事项」里看当前状态。
3. 在对话里说：「基于三个城市的简报和预算，先给我几种真正不同的 Q4 活动方向，写清各自的依据、风险和适合情况，等我选了再做统一方案。」看决策卡如何解释选择条件，再选一条推进。
4. 看收尾卡、产物和 `work-log/`。在「轨迹」中回到当时的决策，试另一条路，比较两条路线的工作与成果；必要时暂停、继续或切回原来的路线。

轨迹样本与方案偏好对可通过本地接口 `GET http://127.0.0.1:58627/api/v1/workspaces/{id}/continuo/export` 查看，请求头带 `Authorization: Bearer <token>`，项目 id 可从 `GET /api/v1/workspaces` 取得；它目前没有界面导出按钮。
