# 轨迹：设计文档

> 状态：设计稿，未实现。对应说明文档 [submission.md](submission.md) §2.2 的「三分支与 worktree」与「任务轨迹与数据闭环」两节。

## 1. 为什么做这个

产品判断是「今天的模型是好的执行者，差的投资人」：让它把一件确定的事做好已经够用，难的是判断哪个方向值得投入。方向的判断留给人，但**人做判断的那一刻必须被记下来**——在什么条件下、有哪些选择、各自的依据是什么、最后选了哪个、选完之后结果如何。

轨迹就是这个记录。它同时是三件东西：

1. **给人看的**：这个项目走到今天，在哪几个岔路口做过选择，为什么。
2. **给 Agent 用的**：下一步该带哪些上下文，哪些可以收起来、需要时再取。
3. **给模型学的**：一条完整轨迹是一个样本；同一个岔路口分出去的两条轨迹，是一对带人类偏好的样本。

第三点不出现在界面上，也不必向用户解释；记在这里，作为为什么要"永不覆盖"的理由。

## 2. 一个心智模型

**轨迹是只读的。任何"改主意"都不是修改，而是复制。**

三种操作在用户那里是三件事，在数据上是同一件事：

| 用户做的 | 实际发生的 |
|---|---|
| 换一个方案 | 在决策点之前复制整条轨迹 → 新轨迹从那里走另一条 |
| 回滚到某一步重来 | 在那一步之前复制整条轨迹 → 新轨迹从那里重新开始 |
| 直接 fork | 在当前节点复制整条轨迹 → 新轨迹接着往下 |

原来那条一个字都不动，状态从"当前"变成"备选"或"已放弃"（放弃要写原因，这句原因本身就是数据）。

这条规则同时解决了三个问题：历史不会被覆盖，所以人能回头看；分支之间没有共享可变状态，所以不会互相污染；每条轨迹都是自洽的一条完整路径，所以可以整条导出。

## 3. 引擎里已经有的：会话 fork

这里的 fork 是**会话 fork，不是 GitHub 那个 fork**。证据：切片函数 `sliceMainRecordsAtTurn(records, sourceSessionId, turnIndex)` 切的是会话的 wire records，按"用户可见的 turn"定位；`wire/tree/fork.ts` 处理的是 `ContextMessage` 与压缩边界；CLI 有 `kimi fork` 子命令（`apps/kimi-code/src/cli/sub/fork.ts`），TUI 有对应命令（`src/tui/commands/session.ts`），node-sdk 有 `forkSession`。GitHub 相关的代码在另一处（`app/plugin/github-resolver.ts`），与此无关。

不需要自己造分叉。Kimi Code 的 `IWorkspaceLifecycleService.fork({ sourceSessionId, turnIndex, title, metadata })` 已经做到：

- 按**用户可见的 turn**切片，复制该 turn 及之前的 wire records 到一个新 session（`packages/agent-core-v2/src/workspace/sessionLifecycle/internal/forkTurnSlice.ts`）；
- 新 session 有自己的目录与 id，源 session 完全不动，新 session 记 `forkedFrom`；
- turn 正在跑时拒绝 fork（`SESSION_FORK_ACTIVE_TURN`）；
- 文件历史记录不进切片，子 agent 记录按时间对齐截断；
- 服务端已有 `POST /api/v1/sessions/{id}:fork`。

所以 Continuo 要加的只是**语义层**：哪条轨迹是哪条的分支、在哪个节点分的、为什么分、现在哪条是当前。执行层直接用引擎的 fork。

这也修正了一个更早的想法：换方案**不是**在原对话后面追加一句"改用方案 B"。那样模型会被方案 A 的全过程锚定。正确的做法是**从决策点之前 fork 出一条干净的线**——B 的 session 里根本没有 A 的执行过程。

## 4. 数据模型

项目状态里增加轨迹层，任务与轮次挂在轨迹上：

```
ContinuoWorkspaceDoc
  activeTrajectoryId
  trajectories: Trajectory[]

Trajectory
  trajectoryId
  label              方案名（2–6 字，和任务名同一套口径）
  sessionId          这条线自己的 session
  status             current | alternative | abandoned
  origin?            { fromTrajectoryId, atNodeId, turnIndex, reason? }
  nodes: Node[]      从根开始的完整节点列表（含被复制的前缀）

Node
  nodeId, at, kind
  kind = task      一件事的开始（任务名、分类、原始要求）
  kind = turn      一轮（prompt / 读 / 写 / 回复）——就是现在的 TaskRound
  kind = decision  一个岔路口（问题 + 2–3 个候选，每个候选带依据与风险）
  kind = choice    人的选择（选了哪个候选、什么时候、放弃别的写了什么原因）
```

`nodes` 是**完整复制**，不是引用父轨迹的前缀。代价是重复存储（每个节点几百字节，一个项目几十个节点，可以忽略），换来的是每条轨迹自洽：导出一条轨迹不需要爬树，删掉父轨迹也不影响子轨迹。

## 5. 一个工具：`Trajectory`

轨迹的全部能力收在一个工具里，用动作区分：

| 动作 | 谁调 | 作用 |
|---|---|---|
| `propose` | 模型 | 开一个决策点，给出若干候选方案：每个带标题、依据、风险、方案文件的地址，以及"选它就发这句话"的 prompt。调用后本轮结束，任务进入"等你选" |
| `expand` | 模型 | 在已有决策点上**追加**新方案（人点「再来几个」时触发），或者判断没得再加、给出停下来的理由 |
| `list` | 模型 | 列出本项目的轨迹与决策点（标题级），以及每个方案文件的地址 |
| `choose` | 人（界面 → 服务端） | 选定一个候选，当前轨迹继续 |
| `fork` | 人 | 从任意节点复制一条新轨迹 |
| `abandon` | 人 | 把一条轨迹标为已放弃，并写下原因 |

模型只能 `propose` / `expand` / `list`：它可以提出岔路、可以再想几个，但**不自己选、不自己开分支、不自己放弃**。方向的判断是人的。这条边界写进工具描述里。

没有 `read` 动作：每个方案和每条轨迹都有**可读地址**（见 §6、§7），模型用普通的 Read 就能取回，不需要为检索再造一个工具。

轨迹状态机：

```
propose ──▶ 等你选 ──choose──▶ current
                   └─未选中──▶ alternative ──fork──▶ 新 current（原 current 变 alternative）
                                             └─abandon──▶ abandoned（带原因）
```

## 6. 方案是怎么生成的

### 6.1 规则

- **数量不设上限，也不规定下限**。模型认为该给几个就给几个；唯一的硬要求是**方案之间必须有区分度**——差别在思路上，不是在措辞上。
- **人可以要更多**。决策卡上有一个显式的「再来几个」，点一次追加一批。这是个明确的动作，不是重新生成。
- **新方案是追加，旧方案永远不删**。加到第四、第五个，前三个仍在原地，可以来回选。
- **模型可以说"没了"**。当已有方案已经覆盖了明显不同的几个方向、再想也只是换皮时，`expand` 返回"停"，并说明为什么停（哪几个维度已经穷尽），同时把**需要人来定的那个点**抛回来——这时候缺的不是方案，是一个判断。这比硬凑第六个方案有用。

### 6.2 方案怎么产出：动态的多 agent，不是派活+汇总

主 agent 不做"分派给三个子 agent 再汇总"。它做的是：**把自己复制几份，每份带一个不同的出发角度，各自走一条独立的线**，并且这几条线之间能互相说话。

- **开局**：主 agent 先想清楚这次要从哪几个角度切（这一步必须有，否则复制出来的都是同一个方案），然后按角度复制自己。每个副本拿到同一套项目上下文 + 自己那个角度。
- **过程中**：每个副本都能看到别人正在写什么。它们共享一个信箱和一个方案目录：能给某一个副本发消息，也能广播；能读别人已经写出来的方案。
- **发现雷同就合并**：如果两个副本发现自己的方案实质相同，可以直接合并成一个，把省下的名额让给真正不同的方向。**不同不是靠隔离逼出来的，而是靠互相知情自觉拉开的。**
- **收敛**：副本各自把方案写成一个文件，主 agent 不做裁决，只把这些文件挂到决策点上交给人。

引擎里已经有一套可以照搬的形状：`features/tower` 的 `TowerSpawn` / `TowerSend` / `TowerInbox` / `TowerFinding` / `TowerMerge`——按名字发消息、广播给 `all`、把发现写进共享目录、带门禁的合并，全部落在 `.tower/comms/` 的文件上，是**文件协议而不是框架调用**，正好是这里要的"通信畅通但不硬性编排"。差别是 tower 绑着 git worktree 与分支评审，那套是给代码任务的；Continuo 复用它的通信形状，不复用它的 git 机制。

### 6.3 成本：别把缓存搞爆

复制副本最容易出事的地方不是并发，是**缓存**。一次 cache read 大约是 input 的十分之一量级，一次 cache write 反而比 input 还贵；如果 N 个副本各写各的缓存，这个功能就没人用得起。

**唯一的原则：共享前缀逐字节相同，差异只能加在末尾。**

1. **fork 天然对齐前缀**。会话 fork 在 turn 边界切片，副本的前缀和母会话逐字节一致，直接命中母会话已经写好的那份缓存，而不是 N 份新的 cache write。这是选用引擎 fork 而不是自己拼上下文的另一个理由。
2. **三条不许动**：不给副本改 system prompt（角度不能写进 system prompt）；不给副本改工具集（工具定义在前缀里）；分叉时刻注入的项目上下文必须是同一份。角度只以**最后一条用户消息**的形式追加——那是唯一允许的差异位。
3. **副本要连着开**。缓存有 TTL（引擎自己就带 `cache_duration` 配置，会话空闲超过它就提示用户缓存已冷）。副本之间拖几分钟，等于每个都重新写一次缓存。
4. **副本只写方案，不做执行**。一个方案是一页纸，通常三五步写完；执行只发生在人选中的那条线上，由一个 agent 做。N 倍只乘在最便宜的那个阶段。
5. **默认 N=1**。方案不需要各自去读不同材料时，主 agent 在一轮里把几个方案直接写出来最省；只有真需要分头探索才复制副本，而且要给出理由。
6. **决策点有预算**：副本数上限、每个副本的步数上限、token 预算。引擎里 tower 已有 `ITowerRateLimitService`（budget / inflight / blockedUntil / acquire-release，被限流时自动降额），照这个形状做。超预算就停下来问人"还要不要再探索几个方向"，而不是默默烧钱。
7. **互相看方案是拉取，不是轮询**。副本写完初稿后读一次别人的方案（一个检查点），而不是每步轮询信箱——每读一次就把别人的内容并进自己上下文的尾部，轮询等于按步数乘 token。注入的也只是别人的标题和一句依据，真要合并时才读完整文件。
8. **用量要看得见**。任务级已经在记 steps / inputTokens / cacheReadTokens / outputTokens；决策点把 N 个副本的用量汇总成一行（"3 个方案 · 缓存命中 92%"）。看得见才管得住。

### 6.4 方案文件

每个方案就是项目里的一个文件，按[工作规范](submission.md)的命名法，用已有的 `plan` 类型：

```
plan-2026-09-23-review-Q4目标-方案A.md
plan-2026-09-23-review-Q4目标-方案B.md
```

这样三件事同时成立：人能直接打开读、能自己改；模型要细节时用 Read 就能取回（这就是"可读地址"）；方案不是藏在应用状态里的一段 JSON，而是项目自己的资产。副本之间的信箱是过程数据，放在 `.continuo/decisions/<id>/` 下，不进用户的视野。

## 7. 上下文管理：收起来，但都留着

模型每一步拿到的不是整棵树，而是**当前轨迹的压缩形式**：

| 内容 | 注入 |
|---|---|
| 项目理解与要点 | 全文 |
| 当前轨迹里已完成的事 | 一行一条：任务名 + 产物路径 |
| 当前这件事 | 完整轮次 |
| 当前轨迹经过的决策点 | 当前选的那个方案：标题 + 依据 + 风险；其余方案：标题 + 一句依据 + 文件地址 |
| 未选中 / 已放弃的轨迹 | 不注入 |
| 其他任何轨迹的执行过程 | 不注入 |

再加一条：**在某个方案上聊了很多轮之后又切走了，那一段不整条带走**，上下文里只留这个过程的一句话（"在方案 A 上往返了 6 轮，落到 X，因为 Y 切走"），完整对话留在那条轨迹自己的地址上。

需要细节时，模型用 Read 打开方案文件或那条轨迹的日志——**从上下文里剔除，不等于丢掉**。这是一次 context 的插拔：默认收起，按需展开，展开的内容随着压缩再次被丢弃，而原始记录始终在文件里。

工具描述里给模型判断依据：用户提到"之前那个方案"、要求对比两版、或者当前材料解释不了某个已有产物时，才去读；否则不读。

## 7. 文件不覆盖

轨迹可以分叉，用户的文件不能凭空回退。三条规则：

1. **新轨迹写到已有产物的同一路径时，加方案后缀**（`2026-09-23-Q4目标-分区域.md` → `…-方案B.md`），两版都留在文件夹里，人能直接比。
2. 每条轨迹记下它产出的文件与当时的 `turnId`，任何一版都能通过 Kimi Code 的 turn 级 file history 取回。
3. **切换轨迹不动磁盘**。轨迹卡上写明"磁盘上这个路径现在是哪条轨迹的产物"，要换回来是一次显式操作。

v4 提到的 worktree 隔离是给代码任务的；文档类项目用上面三条就够，不引入第二套工作目录。

## 8. 界面

- **对话**：始终只展示当前轨迹。决策点在对话里以一张卡出现：问题 + 2–3 个方案（依据、风险）+「走这条」。没有会话切换器，没有并排的对话标签。
- **轨迹**：一棵可缩放的树（缩小＝主干任务与分叉，放大＝节点展开成 背景 / 任务 / 过程 / 结果 四段）。备选分支上有「切换到此方案」，任意节点上有「从这里重来」。
- **记录**：`work-log/` 里的日志文件。每条轨迹的日志独立成文件，文件名带方案名。

三处共用同一套口径（日期 → 事项 → 子事项；标题只写任务名；时间 `YYYY-MM-DD` / `HH:MM`），见 [README.md](README.md)「信息的统一口径」。

## 9. 数据闭环（不进界面）

因为永不覆盖，导出是纯读取：

- **一条轨迹 = 一个样本**：条件（项目约定 + 材料）→ 候选与依据 → 人的选择 → 执行过程 → 产物 → 后续反馈（是否被引用、是否被改、放弃原因）。
- **同一决策点分出的两条轨迹 = 一对偏好样本**，而且偏好是人真实做出的，不是打分打出来的。
- 放弃原因是最稀缺的那一类标注：它说明了"为什么这个方向不值得"，而这正是模型最弱的判断。

## 10. 分阶段落地

| 阶段 | 内容 | 依赖 |
|---|---|---|
| 一 | `propose` + 方案文件 + 人选 + 轨迹记录 + 树（只读展示） | 无，纯新增 |
| 二 | `fork` / `choose` / `abandon`，即换方案与回滚 | 引擎 `fork` 已具备，需补文件后缀策略与轨迹状态 |
| 三 | `expand`（再来几个 / 说没了）与多 agent 生成 | 依赖一；通信形状参考 `features/tower` |
| 四 | 上下文插拔的压缩规则 | 依赖一、二 |
| 五 | 轨迹导出为训练样本 | 依赖一 |

阶段一、二是这个功能的骨架；阶段三、四可以留在文档里，等真实用例再做。

## 11. 未决

- 决策点由模型自行判断"方向不明确"时触发，还是也允许人显式要求"给我几个方案"？倾向两者都要，后者是一句命令。
- 多 agent 生成时，副本数量由主 agent 定还是固定上限？倾向主 agent 定，但设一个成本闸门。
- 副本之间"发现雷同就合并"由谁裁定：发起方自己判断，还是要对方同意？倾向发起方提议、对方确认，留痕在方案文件里。
- 预算超了之后的默认动作：停下来问人，还是先出一个"尽力而为"的结果？倾向停下来问。
- 一个任务里出现多个决策点时，树的纵深会变快；是否需要把一个任务内的连续决策折叠成一层。
- 放弃原因要不要强制填写。倾向：不强制，但空原因的轨迹在导出时标记为低质量样本。
- 轨迹数量上限与归档策略。
