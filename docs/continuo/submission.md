# Continuo 说明文档

Continuo 是一个住在本地文件夹里的 Agent，基于 Kimi Code（fork 自 MoonshotAI/kimi-code）实现。它做三件事：第一次打开文件夹时先理解再动手；把有用的上下文有选择地积累成一份可纠正的账本，每一步给模型看；任务卡住时等你一句话接着干，关掉再开也从上次的位置继续。运行方式和代码位置见同目录的 README。

下面按题目要求的三个方向，各写一个判断、它在产品里落成了什么、demo 里怎么看见。

## 一、交互：入口可以是对话，落点必须是资产

**判断。** 2026 年的 Agent 产品会从"聊天窗口"退回到"工作现场"。用户交出任务之后的部分才是体验的主体：Agent 从哪里拿背景、按什么约定落位、结果放在哪、下次怎么续上。这一层不表现为按钮，但决定了人愿不愿意把工作交出去。显性层只剩三件事：只在需要决定时打断，打断时带着上下文和选项，进度随时可看、可接管。

**落成了什么。** 主窗口是一个工作台而不是聊天框：左边是工作空间和任务记录，中间是文件夹本身，右边才是 Agent。产物直接出现在文件夹网格里，带一个「产物」标记，点它跳到产出这份文件的那次任务。Agent 需要决定时任务进「需要你」，不需要时你可以关掉窗口。人不复述背景，而是在 Context 面板里确认、纠正、停用 Agent 的理解。

**demo 里怎么看见。** 把一条命名约定改成"主题用英文小写连字符"，下一个任务写出的文件名就变了；材料里没有定价决定，Agent 停下来问，你回答一句它在原会话接着干。

## 二、Harness：只建模型学不会的那几层，其余随模型变薄

**判断。** 流程性知识会被模型内化，今天写进 prompt 的"先读再改、先问再猜"三个月后模型自己会做。不会被内化的是四样东西：用户的具体资产和约定、权限边界、外部世界的验证、跨会话的延续。Harness 的价值集中在这四层，其它脚手架应该有退役条件。

**落成了什么。** 在 Kimi Code 的引擎、会话、工具、权限链、问题与审批之上，只新增了一个工作空间账本和围绕它的四个机制：

- **Context 账本**：每条有来源文件、范围、状态（候选 / 生效 / 失效 / 被替代）、修订号。来自 README 这类指引文件的条目直接生效，Agent 自己的推断只是候选。每一步注入，压缩后重新注入。源文件变了，依赖它的条目自动失效，等人说"仍然有效"。
- **交付核验不信模型自报**：Agent 上报的路径和 Harness 观测到的写入合并后逐个检查文件是否存在，才决定"完成"还是"待复核"。验证里有一次 Agent 忘了上报，靠观测写入补上。
- **"等你回复"状态**：模型有时不用提问工具而是一句话问你，如果照常标"完成"，看板就在撒谎。这类结束被标成等你回复，你的回复送回同一会话。
- **一条权限取舍**：Agent 自己的记录工具免审批，因为它写的是账本、可撤销；文件写入仍走审批。验证里 Agent 想顺手改一份旧稿，被拒绝后停手并如实写进"未解决"。

和 Kimi Code 已有机制的边界：`/init` 是一次性写 AGENTS.md，Continuo 的理解有来源、有候选与生效之分、被后续任务持续修正；goal 是自动续跑，Continuo 的续接始终由人触发，避免和"用户暂停"打架；fileHistory 是撤销的安全网，Continuo 只借它的来源做核验。

**demo 里怎么看见。** 一次任务结束，看板卡片上是核验过的产物路径和未解决项；改一下材料再打开，Context 面板里有一条被标成"来源已变化，暂不生效"。

## 三、模型：长上下文变便宜之后，压缩的目的从省钱变成保注意力

**判断。** K3 这一代把长上下文和连续几十小时任务当成目标场景，缓存命中价把"每一步重新交代背景"从贵变成可承受。于是 Harness 里"为省 token 尽早摘要"的压力在下降，剩下的问题是每一步给模型看什么、以什么顺序。另一个约束是前缀缓存只对完全相同的前缀整体有效，"稳定前缀、变化只追加"的纪律在 K3 上比在别的模型上更要紧。

**落成了什么。** Context 注入放在每步的提醒位而不是改 system prompt，稳定部分一字不动；账本按决定 > 约定 > 进度 > 背景 > 材料排序，先当排序用，预算放开时不用改逻辑。两处替模型补课的兜底（等你回复、观测写入）都标了退役条件：当模型在评测集上的提问工具使用率和上报率稳定超过阈值，就从默认开改成只记日志。

**还想做但没做的。** 用户纠正账本的那一刻，"纠正前的条目 + 纠正后的条目 + 当时的任务"是一条天然的偏好数据；产品只需把它导出成一致格式。这是"最挑剔的用户驱动迭代"的机器版本。

## 四、验证与限制

验证（Kimi 账号，模型 kimi-for-coding，合成数据的演示文件夹）：首次打开约 60 秒产出理解与 5 条条目；纠正命名约定后下一任务遵守；材料缺决定时 Agent 停下询问，回复后同会话续接，中途暂停再继续无重复写入；一次交付靠观测写入核验，一次上报含未解决项进待复核；越界修改被拒后停手；重开不重跑初始化，材料变更后条目失效。单测 11 个，类型检查与 lint 通过。

限制：兜底只观测 Write / Edit，Shell 写入看不见；同一工作空间一次只跑一个任务；失效只按文件大小和修改时间判断；文件工作区只读；功能在实验开关后面，默认关闭。

## 五、下一步

1. 多任务并发 + 决策收件箱：所有卡点攒在一处，人空了统一处理。
2. 改动集核验：任务开始建基线，结束比对真实改动，冲突另存，逐文件接受或放弃。知识工作者没有 git，这一层是产品替他们补的。
3. 任务范围围栏进策略链：契约之外的写入直接拒绝，不再靠人点拒绝。
