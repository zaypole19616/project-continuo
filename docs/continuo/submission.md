# Continuo：让 Agent 把工作持续接住

我的判断是：2026 年，模型能独立完成的任务会越来越长，人与 Agent 的协作会从"一次对话"变成"围绕一个项目持续工作"。用户交代目标、在关键点作决定、回来时接着改。产品要做的，是给这段工作一个稳定的落点，并且让人始终知道 Agent 理解了什么、正在做什么、做成了没有。

Continuo 是一个住在本地文件夹里的 Agent，基于 Kimi Code 实现。它第一次打开文件夹时先理解再动手；把有用的上下文有选择地积累成一份可纠正的账本；需要决定时停下来问；任务结束时核验产物是否真的存在；关掉再开，从上次的位置继续。

## 1. 对未来 Agent 产品交互、Harness 与模型发展趋势的判断

### 1.1 对产品交互的三个思考

我把人与 Agent 的协作体验分成两层。一层是**显性交互**：GUI、语音、主动提醒这些用户看得见的界面与选择，包括 Agent 什么时候主动出现、什么时候停下来确认。另一层是**隐性交互**：用户把任务交出去之后，Agent 怎么获取上下文、怎么组织工作、把结果放在哪里。它不表现为按钮或对话，却决定了用户对这个 Agent 的感受。这组划分借用交互设计里的 explicit / implicit interaction：显性的由人发起、需要注意力；隐性的由系统基于对情境的理解替人完成。两层合在一起，才是完整的协作体验。

围绕这两层，我有三个 bet。

**Legibility · 有章法**（隐性层）。好助理做完事，东西在该在的地方，名字一看就懂，下次不用问。我希望 Agent 的每次输出都有对应的位置和一致的命名，重要的约定能留下来，下次继续时不用从头交代。这里的关键不是把所有对话都存起来，而是**有选择地积累有效上下文：留下有来源、有适用范围、能修正、会失效的理解。** 这些东西不会表现为一个新功能，但会让人愿意把工作交出去。

**Proactiveness · 主动有分寸**（显性层）。主动型 Agent 最常见的失败，是把"让用户注意到我"当成目标：悬浮窗、鼠标旁的弹窗、不断的提醒。它本该减少负担，却在抢注意力。我认为好的主动是润物细无声的：在已经明确委托的范围里把事情处理好，不需要人盯着；需要人作决定时，带着必要的信息来找我；我想查看进展、修改要求、接管或暂停，随时都能做到。判断一次介入值不值得，标准只有一个：预期收益是否超过打断的代价。

**Clarity · 坦诚与清晰**（两层都有）。AI 是新东西，用户往往不知道自己在选什么。之前做 PPT 生成时有两条路线：图片式效果好但不能编辑，传统格式可编辑但视觉弱。不先讲清差异就直接做，最后交付的可能不是用户想要的。后来我们在任务开始前把两种格式的特点摆出来让用户选，用户知道自己选了什么、会得到什么，Agent 也不在需求没对齐时往下做。我从中提炼的原则借自增长实践：**一个步骤如果不帮用户理解"这为什么适合我"，就是摩擦，砍掉；如果能帮他理解什么对他最相关，哪怕增加摩擦也要留下，然后去测。** 它在显性层是开工前的选择，在隐性层是每条理解都标来源、完成由文件证明而不是由模型自报。

### 1.2 对 Harness 与模型发展趋势的判断

今天大家都在谈 Agent 的下一阶段能力：long horizon、递归自我改进。实际体验里，让模型把一件具体的事执行到底，它已经很强；**但判断哪个方向更有价值、哪里值得继续投入，是它的弱项。** 模型在各类任务里常常分不清什么更值钱、什么该放弃。我认为这是 long horizon、自我改进、乃至泛化到真实任务的共同卡点。原因不是模型不够聪明，而是"值钱"在它的训练里从来不是一个可观测的量。

一句话概括：**今天的模型是好的执行者，差的投资人。** 围绕这一点，我的 bet 有四条。

第一，**把方向判断从模型里拿出来，做成 Harness 里的显式对象。** Agent 遇到分叉时不自己押注，而是产出选项、各自的收益、代价和可逆性，人来决定。这不是退让，是分工：模型擅长把一个选项执行到底，人擅长在选项之间下注。

第二，**Harness 的核心工作是把世界的反馈接回来，让"值钱"变成可观测的量。** 交付物是否真的存在、用户接受还是放弃、产物之后有没有被用到、哪些判断被人纠正过。这些信号今天散落在产品里没人收。收起来，长任务才有可以对齐的中间奖励，自我改进才有方向感。

第三，**把"判断"变成"比较"。** 模型做绝对判断差，做成对比较明显更稳，评测里 pairwise 比打分靠谱就是这个现象。分叉时不要求它先想对，而是让几个方向各推进一小段、各出一页摘要，在摘要之间比较。方向判断弱的时候，用小预算和可逆性兜住损失。

第四，**方向判断能力的提升，会来自带人类决策标签的真实任务轨迹，而不是更长的上下文或更多的自我博弈。** 人在第一条里做的每一次选择，加上第二条收回来的结果，是训练价值判断的真实来源。所以这个阶段的产品同时是数据采集器，产品与模型一起设计的意义就在这里。

模型侧还有一个具体约束影响 Harness 设计：长上下文和缓存命中正在变便宜，"为省 token 尽早摘要"的压力在下降，压缩的目的从省钱变成保住任务状态和注意力质量；同时前缀缓存只对完全相同的前缀整体有效，"稳定前缀、变化只追加"的纪律比以前更要紧。

## 2. 产品功能点

### 2.1 产品功能

Continuo 面向一个本地文件夹，界面是一个工作台：左边是文件夹和任务记录，中间是对话，右边是文件夹本身和「记住的事」。界面里不出现 Context、Legibility 这类词，只说人话；英文名只留在介绍页和这份文档。按用户的一次完整使用来说：

1. **打开文件夹，先理解再动手。** 一个只读的 Agent 扫描目录、优先读 README 这类指引文件、抽样几份材料，然后写下一段"我对这个文件夹的理解"和若干条它记住的事（约定 / 背景 / 决定 / 进度 / 材料）。来自指引文件的条目直接生效；Agent 自己的推断只是候选，在理解卡里一键确认或忽略。每条都带来源文件，点开就能看。
2. **交代任务，它带着有效 context 干活。** 每个任务一个独立会话。Harness 在每一步把生效的条目按 决定 > 约定 > 进度 > 背景 > 材料 编成一段参考数据注入，压缩后重新注入。你改一条约定，下一个任务立刻照新规矩落位、命名。
3. **缺决定时停下来问，回一句接着干。** 材料里没有的决定它不编，停下来问你；你回复后在同一会话续接。中途可以停止，再点继续，它先重读文件再补剩余部分，不重复写。
4. **完成由文件证明。** 任务结束时，Harness 把 Agent 上报的产物路径和它实际写过的文件合并，逐个核验存在，才标"完成"；没做到的如实列出，标成"还差一点"。每个任务以一张收尾卡结束：做了什么、放在哪、这次记住了什么，以及**这次用上了几条记住的事、追问了几次**——"不用重新交代"由此变成一个可以看见的数字。产物出现在右侧文件夹里，带「产物」标记，点它回到产出它的那次任务。
5. **关掉再开，接着干。** 不重跑理解；正在跑的任务标为中断可续；如果某条记住的事依赖的材料在两次打开之间变了，这条会标成"来源变了，先不用"等你确认。

演示文件夹自带一段历史：上次起草的初稿、上周口头定下的定价决定、"改稿另存新文件"的规矩。所以一打开就是"第二次打开"，没有等待；第一张体验卡是"接着上次的初稿，把定价那节改成上周定的方案"——它直接找到旧稿、按记住的决定改、另存新文件，收尾卡上写着"用上了 7 条记住的事，追问 0 次"。这一幕就是 Continuo 和普通会话的区别。想看真实的首次理解过程，理解卡上有"重新了解"；打开自己的文件夹时走的也是真实过程。

对话里的关键卡片带一个小标签，写明它体现的是哪一条判断，点标签能看到那条判断的完整说明。

### 2.2 Harness 改动

Kimi Code 的引擎、会话、工具、权限链、提问与审批、持久化全部原样复用。Continuo 只新增一个工作空间账本和围绕它的机制，通过 Feature seam 挂进引擎，核心零改动，整个功能在实验开关后面。

| 新增 | 解决什么 |
|---|---|
| Context 账本：条目有来源、范围、状态（候选 / 生效 / 失效 / 被替代）、修订号 | AGENTS.md 是人写的静态文件；这里的 context 是有选择地积累出来的，能纠正、能失效、能追溯 |
| 每步注入 + 压缩后重注（走引擎的 Reminder 机制） | 长任务里背景不丢，且稳定前缀不动、变化只追加 |
| 首次打开的只读理解任务（独立 profile，只有读和记录工具） | 先理解再动手；和 `/init` 的区别是有来源、分候选与生效、被后续任务持续修正 |
| 交付核验：上报路径 ∪ 观测到的写入 → 逐个 stat | "模型说完成"不等于完成；Agent 忘了上报也不丢 |
| "等你回复"状态 | 模型有时不用提问工具而是一句话问你，若照常标完成，界面就在撒谎 |
| 源文件指纹与失效 | 材料变了，基于旧材料的判断不该继续生效 |
| 自动进度条目 | 下一个任务、下一次打开知道哪些已经做过、产物在哪 |
| 记录工具免审批，文件写入仍审批 | 记账本是可撤销操作，每次弹审批把最该无感的动作变成打扰；写用户文件必须问 |

与 Kimi Code 已有机制的边界：goal 是跨 turn 的自动续跑，Continuo 的续接始终由人触发，避免和"用户暂停"打架；fileHistory 是撤销的安全网，Continuo 只借它的来源做核验，不把它当审查对象。

### 2.3 验证与边界

用 Kimi 账号、kimi-for-coding 模型、合成数据的演示文件夹跑通了整条链路：首次打开约一分钟产出理解与五条条目；改命名约定后下一任务遵守；材料缺定价决定时 Agent 停下询问，回复后同会话续接，中途暂停再继续无重复写入；一次 Agent 忘了上报，靠观测写入补齐并核验；一次上报含未解决项进待复核；越界修改被拒后停手；重开不重跑，材料变更后条目失效。演示夹自带历史后再验一次："接着上次"任务 4 步完成，用上 7 条记住的事、0 次追问，产物另存为新文件，并自己说明定价决定的来源是口头确认而非材料。单测 12 个，类型检查与 lint 通过，上游全量测试不受影响。

边界：观测只覆盖 Write / Edit，Shell 写入看不见；同一工作空间一次只跑一个任务；失效只按文件大小和修改时间判断；文件区只读；没有定时自主推进。同模型的对照里，普通 Kimi 会话也能完成理解、纠正、提问和连续编辑，所以这次验证的是：怎样让这些能力在持续项目里更容易被理解、干预和恢复。

### 2.4 运行与材料

环境 Node ≥ 24.15、pnpm 10.33。在项目根目录：

```sh
pnpm install
pnpm run build:packages && pnpm -C apps/kimi-code run build
node apps/kimi-code/dist/main.mjs login
KIMI_CODE_EXPERIMENTAL_CONTINUO=1 node apps/kimi-code/dist/main.mjs web --no-open --port 58627
```

另开一个终端 `KIMI_PORT=58627 pnpm dev:continuo`，打开 `http://127.0.0.1:5180/#token=<启动时打印的 token>`。首页可以一键用演示文件夹开始，也可以打开自己的文件夹。文件留在本机，被读取的文本会随请求发送给所配置的模型。

代码：引擎侧 `packages/agent-core-v2/src/features/continuo/`，服务侧 `packages/kap-server/src/continuo/`，界面 `apps/continuo/`，测试 `packages/agent-core-v2/test/features/continuo/`。
