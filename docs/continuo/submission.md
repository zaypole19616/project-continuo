# Continuo：让 Agent 把工作持续接住

Continuo 是一个住在本地文件夹里的 Agent，基于 Kimi Code 实现。它第一次打开文件夹时先理解再动手；把有用的上下文有选择地积累成一份可纠正的账本；需要决定时停下来问；任务结束时核验产物是否真的存在；关掉再开，从上次的位置继续。

## 1. 对未来 Agent 产品交互、Harness 与模型发展趋势的判断

### 1.1 对产品交互的三个思考

我把人与 Agent 的协作体验分成两层。一层是**显性交互**：是产品形态，是用户看到的界面，如以对话框为主的桌面端 Agent Codex、Manus，以 IM 交互为主的 grok bot 等等。移动互联网发展至今，不同的需求场景，早已有了最适配的产品交互形态。比如，用户在自己工作时，可以打开桌面端，在对话框里完成任务；和别人协作时，又可以回到 Slack 这样的协作软件里与 Agent 交互。这些形态可以互相配合，背后也可以由同一套 Agent Harness 支撑。我认为，产品形态应该去适配用户的需求场景。可能不存在唯一正确的交互，应该让 Agent 出现在用户最熟悉的产品形态下。

另一层是**隐性交互**：是 Agent 在执行与交付中让人感受到的做事方式，比如怎么了解资料、组织工作、保存成果。作为助理，我们会希望它把事情打理得井井有条。这有点像我们平时说的 P 人或 J 人，用户能感受到这个 Agent 是怎么做事的，也会因此对它形成不同的使用体验。

两层合在一起，才是完整的协作体验。围绕这两层，我有三个 bet。

### Orderliness · 有条理和章法

我希望 Agent 能把工作打理得有条理：资料、任务与成果各有归处，用户的做事方式及习惯能留下来，下次继续时不用从头交代。重点是选择性积累有效上下文：**留下有来源、有适用范围的客观信息。**

### Proactiveness · 主动但有分寸

主动型 Agent 最常见的失败，是把“让用户注意到我”当成目标：悬浮窗、鼠标旁的弹窗、不断的提醒。它本该减少负担，却在抢注意力。我认为好的主动是润物细无声的：在已经明确委托的范围里把事情处理好，不需要人盯着；需要人作决定时，带着必要的信息来找我；我想查看进展、修改要求、接管或暂停，随时都能做到。

### Clarity · 坦诚与清晰

AI 发展迅速，新的概念或功能可能给用户带来较高的理解成本。以往的产品经验往往会让我们觉得，一款产品应该足够直观，没有任何教程或引导，凭直觉就能直接上手使用，但现在这样做反而可能提高用户的使用门槛。所以需要帮助用户理解什么对他们最相关，即便会增加理解成本或摩擦，也不要回避。

### 1.2 对 Harness 与模型发展趋势的判断

今天大家都在谈 Agent 的下一阶段能力：long horizon、递归自我改进。实际体验里，让模型把一件具体的事做好，它已经很强；但判断哪个方向更有价值、哪里值得继续投入，是它的弱项。模型在各类任务里常常分不清什么方向更有价值。我认为这是 long horizon、自我改进，乃至泛化到真实任务的共同卡点。

我认为这是当下比较难解决的问题，需要在模型、Harness，乃至产品交互这三个层面一起尝试解决，构建模型、Harness 与产品之间的反馈闭环。

一句话概括：**今天的模型是好的执行者，差的投资人。** 围绕这一点，我的 bet 有三条。

第一，**通过 Harness 记录人的判断与反馈。** 用户在什么情况下选择了哪个方向，为什么修改要求，接受或放弃了哪些结果，这些信息都应该和当时的任务一起留下来。

第二，**把一些判断做成比较，再根据实际结果收集反馈。** 遇到需要判断方向的任务时，可以先给出几个可能的方向，让用户比较和选择；继续推进后，再记录产物有没有被采用、哪些地方被修正过。这样留下来的既有当时的选择，也有选择之后的实际结果。

第三，**让模型从这些带有人类判断与结果反馈的任务轨迹中学习，提高方向判断的能力。** 产品提供交互，Harness 记录过程与反馈，模型再从中学习，逐步形成这样的数据闭环。

## 2. 产品功能点

### 2.1 产品功能

#### Orderliness：AGENTS.md 工作规范

AGENTS.md 约定了 Agent 在项目中的工作方式：开工前阅读目录指引，按既有结构确定产出位置；文件统一按日期、分类和任务命名；每项任务建立工作日志，记录开始时间、输入目录、输入文件、输出文件等 metadata，以及用户原始要求、每轮处理过程和最终产出。项目型任务同时保留 STAR 框架，在用户确认阶段完成后补全。收尾时同步工作记录、目录导航和相关项目文档。

通用工作规范与项目约定分开维护。项目中的具体规则保存在对应目录，Agent 按当前任务所在目录读取适用的约定。

#### Proactiveness：打开已有文件夹，主动了解现有工作

用户选择已有文件夹后，Agent 先读取 AGENTS.md 和目录指引，再沿指引查看相关材料，了解现有内容、目录结构、文件命名和内容格式。已有的组织方式继续沿用，并保留有来源、适用范围明确的项目要点。

了解过程中，用户可以浏览文件或直接交代任务。Agent 在委托范围内继续推进，缺少关键决定时提问；用户可以暂停、补充要求或继续。任务结束后，最多提出一项有依据的下一步建议，由用户选择是否开始。

#### Clarity：使用引导与过程查看

首次打开时，通过简短引导介绍资料组织、主动推进和重要选择。工作过程中，用户可以查看项目理解及其来源、任务状态、工作记录和成果。准备摘要默认折叠，详细过程在工作记录中查看；成果支持预览和版本对比，未完成的事项单独列出。

### 2.2 Harness 改动

复用 Kimi Code 的模型调用、Agent Loop、Session、工具与提问机制，新增项目上下文、任务状态和交付核验。有效上下文通过 Reminder 提供给模型；任务支持等待回复、暂停与续接，交付时核验实际文件及相关状态。

#### 判断与反馈记录

按任务保存用户的原始要求、补充信息和关键决定，关联已读取的资料与成果。上下文区分项目范围和任务范围，并保留来源；成果版本关联当时的输入和上下文版本。工作记录由任务状态生成，按日期和事项展示。

#### 三分支与 worktree（待实现）

对于方向尚不明确的任务，提供 3 条候选路径及各自依据。用户选择一条推进，其余分支保留；后续可以返回决策点，切换到另一条路径。每个分支独立保存任务状态、上下文和产物版本，代码任务通过 worktree 隔离工作目录。

#### 任务轨迹与数据闭环（待实现）

将任务条件、候选路径、用户选择、执行过程、产物和后续反馈关联为完整轨迹。反馈包括成果是否被采用、哪些内容被修改，以及放弃某个方向的原因；轨迹用于后续评估与模型训练。

当前两份原型分别实现了上述功能的部分基础，尚未合并为同一产品。工作记录目前由应用状态生成；完整按 AGENTS.md 写入项目内 work-log 的流程、三分支恢复、worktree 隔离和训练数据流程尚未实现。

## 3. 运行

环境 Node ≥ 24.15、pnpm 10.33。在项目根目录：

```sh
pnpm install
pnpm run build:packages && pnpm -C apps/kimi-code run build
KIMI_CODE_EXPERIMENTAL_CONTINUO=1 node apps/kimi-code/dist/main.mjs web --no-open --port 58627
```

另开一个终端 `KIMI_PORT=58627 pnpm dev:continuo`，打开 `http://127.0.0.1:5180/#token=<启动时打印的 token>`。打开是一张启动卡：新建项目、打开已有项目、最近打开的项目；进入项目后左边是文件窗口，右边挂着对话，一个项目一个会话，每件事做完在项目的 `work-log/` 留一份日志。第一次启动有一段简短引导；深浅色跟随系统，右上角可切换。首次未配置模型时，先运行 `node apps/kimi-code/dist/main.mjs` 并在 CLI 里 `/login`。文件留在本机，被读取的文本会随请求发送给所配置的模型。

实现细节与边界见 [docs/continuo/README.md](README.md)。
